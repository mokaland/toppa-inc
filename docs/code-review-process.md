# TOPPA Inc. コードレビュープロセス

> 作成: CTO マルコ・ロッシ
> 日付: 2026-02-16
> ステータス: ドラフト

## 1. 目的

TOPPA Inc. のプロダクト品質向上、技術的負債の抑制、チームメンバー間の知識共有を促進するため、効果的なコードレビュープロセスを確立する。

## 2. レビュー対象

- 全ての新規機能開発
- バグ修正
- リファクタリング
- 技術スタックの変更

## 3. レビュー担当者

- Founding Engineer (カルロス・メンデス) が作成したコードは、CTO (マルコ・ロッシ) がレビューする。
- 緊急性の高いバグ修正など、状況に応じて複数名のレビューを推奨する。

## 4. レビューのタイミング

- GitHub Pull Request (PR) 作成時
- PRが `develop` ブランチまたは `main` ブランチにマージされる前

## 5. レビュー項目

### 5.1. 機能要件の充足

- プロダクト仕様書 (PdM作成) に記載された機能要件が全て満たされているか。
- エッジケースやエラーハンドリングが適切に考慮されているか。

### 5.2. コーディング規約の遵守

- `AI_PLAYBOOK.md` に記載されたコーディング規約 (TypeScript strict mode, 型定義必須, any禁止, camelCase/PascalCase) が守られているか。
- ESLint, Prettier などの自動フォーマットが適用されているか。

### 5.3. テスト

- 適切なユニットテスト、E2Eテストが記述されているか。
- テストカバレッジが目標値 (80%) を満たしているか。
- `run_tests` でテストが正常にパスすることを確認済みか。

### 5.4. パフォーマンス

- パフォーマンス要件 (技術方針書に記載) を満たしているか。
- 無駄な処理やボトルネックとなる可能性のある箇所がないか。

### 5.5. セキュリティ

- `docs/tech-direction.md` に記載されたセキュリティ方針に準拠しているか。
- 脆弱性につながる可能性のある実装がないか (例: SQLインジェクション、XSS対策)。

### 5.6. 可読性・保守性

- コードが理解しやすいか (命名規則、コメント、構造)。
- 将来的な変更や拡張が容易な設計か。
- 不要なコードや重複がないか。

### 5.7. ドキュメント

- 必要な箇所にJSDocコメントが記述されているか。
- APIドキュメントなどが最新の状態に保たれているか。

## 6. レビュープロセス

1.  **PR作成**: Founding Engineer が機能開発ブランチから `develop` ブランチへPRを作成する。
2.  **自動チェック**: GitHub Actions が Lint, Type Check, テストを自動実行する。
3.  **レビュー依頼**: Founding Engineer はPRのレビュー担当者 (CTO) を指定する。
4.  **コードレビュー**: CTO はPRの内容を確認し、コメントや修正依頼を行う。
5.  **修正**: Founding Engineer はレビューコメントに基づきコードを修正する。
6.  **承認**: CTO が最終的なコードを承認する。
7.  **マージ**: Founding Engineer は `develop` ブランチへPRをマージする。

## 7. コミットメッセージ

- AGENTS.md に準拠したコミットメッセージ (`[ロール名] 内容`) を使用する。

## 8. ツール

- GitHub Pull Request 機能
- GitHub Actions (CI/CD)
- ESLint, Prettier
- Vitest, Playwright

## 9. 改善

- 定期的にレビュープロセスの効果を評価し、必要に応じて改善を行う。
